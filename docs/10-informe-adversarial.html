BUG-35 · Aprobación repetida sobre Approved

Regla: RN-40. Severidad: Media / Alta.

Después de aprobar legítimamente un gasto PendingApproval, una segunda llamada a approve devuelve HTTP 200. Debía devolver 4xx y no registrar una nueva decisión.

Reproducir con cURL
curl -k -X PUT -H 'Authorization: Bearer <APPROVER_TOKEN>' '<API>/api/v1/approvals/<APPROVED_EXPENSE_ID>/approve'

Trace · reproducción API 3/3.

BUG-36 · Rejected puede pasar a Approved

Reglas: RN-40, riesgo sobre RN-44/RN-50. Severidad: Alta / Alta.

Después de rechazar con motivo válido, approve responde HTTP 200 y cambia el estado final Rejected a Approved. Debía responder 4xx y conservar Rejected.

Reproducir con cURL
curl -k -X PUT -H 'Authorization: Bearer <APPROVER_TOKEN>' '<API>/api/v1/approvals/<REJECTED_EXPENSE_ID>/approve'

Trace · reproducción 2/2.

Controles conformes y falsos positivos

  • Employee no lee detalle/historial ni elimina gastos ajenos.
  • Manager no decide gastos fuera de su alcance; Employee no aprueba; Finance no elimina gastos ajenos.
  • Self-approval devuelve 403.
  • Mass assignment de owner/status/expenseNumber se ignora.
  • JSON null/array/string, método incorrecto e IDs manipulados responden 4xx sin mutación.
  • Logout con bearer reutilizable es coherente con el servidor stateless documentado.

Descartados: lectura global de Administrator es permitida en modo solo lectura; FinanceController (+Employee) puede crear gastos propios. Reportarlos como vulnerabilidades habría contradicho el Anexo G.
